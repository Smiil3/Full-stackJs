# Décisions frontend

Décisions non bloquantes prises côté front (option la plus sûre), avec leur justification.
Les points tranchés par le PO sont référencés par la version du contrat.

| # | Sujet | Décision | Pourquoi |
|---|---|---|---|
| D1 | Chemin du cookie de refresh | On suit le contrat : `Path=/api/v1/auth` (le plan disait `/api/auth`, corrigé par le PO). | Contrat = source de vérité. |
| D2 | TypeScript 6.0.x (et non 7) | Version épinglée à 6.0.3. | `typescript-eslint` ne supporte pas encore TS ≥ 6.1 ; le lint typé est indispensable pour l'audit. |
| D3 | ESLint 9 (et non 10) | Épinglé à 9.x. | `eslint-plugin-jsx-a11y` (accessibilité) ne déclare pas encore la compatibilité ESLint 10. |
| D4 | Worker MSW | Servi uniquement par le serveur de dev (`npm run dev:mock`) via un plugin Vite `apply: 'serve'`, jamais copié dans `dist/`. Le code de mock est importé dynamiquement derrière `import.meta.env.MODE === 'mock'` ⇒ éliminé du build. | Aucune infrastructure de mock en production. |
| D5 | Service worker PWA | Ne met en cache que la coquille applicative (JS/CSS/HTML/icônes). **Aucune réponse d'API** n'est mise en cache par le service worker. Le hors-ligne métier (billets, snapshot scanner) passe par IndexedDB avec purge à la déconnexion. | Une réponse d'API en cache HTTP survit au logout et ne se purge pas finement. |
| D6 | Démarrage hors-ligne | Un refresh en échec **réseau** (≠ 401) ne déconnecte pas : statut `offline`. Validé par le PO. | Scanner et billets doivent rester utilisables sans réseau. |
| D7 | Refresh proactif | En plus du refresh réactif sur 401 `UNAUTHENTICATED`, un refresh est planifié à `max(expiresIn − 60 s, expiresIn / 2, 10 s)`. Les deux passent par la **même** promesse partagée. Validé par le PO ; plancher ajouté en F1.1. | Moins de 401 sur mobile, pas de tempête ni de boucle de refresh. |
| D8 | Messages d'erreur | Le front n'affiche jamais `error.message` du serveur : il traduit le `code` contractuel en message français (`src/api/errors.ts`). Seuls les messages de champ de `VALIDATION_ERROR` sont affichés (en texte). | Messages stables, compréhensibles, sans fuite technique. |
| D9 | Chemins d'API | Tout paramètre interpolé dans un chemin passe par `apiPath\`…\`` (encodage `encodeURIComponent`). | Un identifiant forgé ne peut pas changer de route. |
| D10 | Requêtes | `cache: 'no-store'` et `redirect: 'error'` sur tous les appels API, délai max 15 s. | Pas de données personnelles dans le cache HTTP ; une redirection inattendue n'est pas suivie silencieusement. |
| D11 | Admin plateforme pour un non-admin | 404 (figé en contrat v1.4). | Ne révèle pas l'espace d'administration. |
| D12 | Liste d'attente désactivée | 409 `WAITLIST_DISABLED` (contrat v1.4) ; le front masque aussi le bouton si `rules.waitlistEnabled = false`. | UX ; le serveur fait foi. |
| D13 | Saisie des dates en back-office | Saisie dans le **fuseau de l'événement** ; une heure inexistante (passage à l'heure d'été) est décalée après le saut et signalée, une heure ambiguë (passage à l'heure d'hiver) prend la 1ʳᵉ occurrence et est signalée (`zonedInputToUtc`). | Aucune ambiguïté silencieuse pour l'organisateur. |
| D14 | Paiement en mode mock | En `dev:mock`, `redirectUrl` pointe vers une page interne `/mock-psp/:orderId` (chargée uniquement en mode mock) ; le « webhook » est appliqué après 3 s pour exercer le polling. En réel, seules les redirections vers l'origine du PSP configurée ou la nôtre sont suivies. | Le mock tourne dans la page : un rechargement perdrait l'état en mémoire. |
| D15 | Génération de session (F1.1) | Compteur incrémenté à chaque login / logout / fin de session ; un refresh lancé sous une génération antérieure est ignoré (`SESSION_CHANGED`). Login et logout attendent le refresh en vol. | Pas de token réinjecté après logout, pas d'effacement d'un login récent par un 401 tardif. |
| D16 | Multi-onglets (F1.1) | Refresh, login et logout sérialisés par `navigator.locks` (`nuits-refresh`) ; login/logout propagés par `BroadcastChannel('nuits-auth')` (type d'événement seulement, jamais de jeton). Navigateur sans Web Locks : pas de sérialisation (dégradation documentée). | La réutilisation d'un refresh token révoque toute la famille côté back. |
| D17 | Seul `INVALID_REFRESH_TOKEN` déconnecte (F1.1) | Un 403 `CSRF_CHECK_FAILED`, un 5xx ou une coupure réseau sur `/auth/refresh` laissent la session locale intacte. | Éviter les déconnexions intempestives. |
| D18 | CSP (F1.1) | `security-headers.ts` : CSP stricte (aucun `unsafe-*`) pour `preview` et la prod (`deploy/`), assouplie uniquement pour le serveur de dev (préambule React Refresh inline, styles injectés, WebSocket HMR). | Le dev Vite ne fonctionne pas sans ; jamais servi en prod. |
| D19 | Rejeu des requêtes (F1.1) | Une requête n'est rejouée qu'une fois, après 401 `UNAUTHENTICATED` + refresh réussi. Jamais de rejeu auto sur réseau/5xx. `POST /orders` sans `Idempotency-Key` UUID est refusé par le client avant envoi. | Pas de double commande. |
| D20 | `deviceId` du scanner | Sera stocké dans l'IndexedDB du scanner (`src/scanner/db.ts`), pas en localStorage (interdit par le lint). | Un seul emplacement de persistance contrôlé. |
| D21 | Vérification d'email (F2) | Confirmation par **bouton** sur `/verify-email`, jamais automatiquement au chargement ; le jeton est retiré de la barre d'adresse dès la lecture (idem `/reset-password`). | Les antivirus de messagerie ouvrent les liens et consommeraient le jeton à usage unique. |
| D22 | Redirection vers le PSP (F2) | `redirectUrl` suivi seulement s'il pointe vers notre origine (navigation interne validée) ou vers `VITE_PSP_ORIGIN` (https obligatoire en production, http toléré pour localhost en dev). Sinon : redirection bloquée et message. | Anti open-redirect / phishing si la réponse était altérée. |
| D23 | Fin de session volontaire (F2) | Avant une action qui révoque toutes les sessions (changement de mot de passe), la page déclare la destination de fin de session ; la garde de route l'utilise quelle que soit la requête qui constate la révocation en premier. | Évite la course avec les requêtes de fond (401 → refresh refusé). |
| D24 | Démarrage anonyme (F2) | Le refus du refresh au démarrage sans compte ne vide pas le cache (aucune donnée privée) : seules les données hors-ligne sont purgées. | Corrige un blocage des pages publiques. |
| D25 | Remboursement affiché avant annulation | Contrat v1.6 : le front affiche `refundPreviewCents` calculé par le serveur ; bouton d'annulation proposé seulement s'il est non nul. Aucun calcul côté client. | Le serveur fait foi. |
| D26 | Règles de vente (F3) | Chaque paramètre a un mode « réglage du collectif » (envoie `null`) ou « personnalisé » ; la valeur effective affichée = personnalisée sinon collectif. Montants en euros et pourcentages convertis par analyse de chaîne (centimes / points de base), jamais par flottant. | Pas d'erreur d'arrondi, héritage explicite. |
| D27 | PATCH d'événement (F3) | Seuls les champs modifiés sont envoyés ; une date n'est renvoyée que si sa saisie a changé. | Évite un faux « report » (arrondi à la minute) et les écrasements concurrents. |
| D28 | Report (F3, contrat v1.7) | Si l'événement a des places vendues ou réservées (`sold + held > 0`) : dates verrouillées pour un MANAGER ; pour l'OWNER, confirmation forte avec motif obligatoire avant l'envoi de `rescheduleReason`. | Le serveur fait foi (403/400), l'écran évite l'impasse. |
| D29 | Coordonnées bancaires (F3) | IBAN jamais pré-rempli ni affiché en clair (masque serveur) ; ressaisie complète + mot de passe actuel ; contrôle UX mod 97 + longueur par pays SEPA ; `INVALID_CREDENTIALS` affiché sur le champ mot de passe sans déconnexion. | Donnée sensible, ré-authentification (v1.7). |
| D30 | Tableau de bord (F3) | Polling 5 s (`refetchIntervalInBackground: false`), fraîcheur mesurée sur l'horloge LOCALE (`dataUpdatedAt`), alerte si hors-ligne, en erreur ou non rafraîchi depuis 15 s. | Fiable sur mobile ; pas de décalage d'horloge sur une durée locale. |
| D31 | Export CSV (F3) | `fetch` authentifié (Bearer) → `Blob` → `URL.createObjectURL` → lien de téléchargement local, révoqué ensuite. Jamais de jeton dans une URL. | Exigence du brief. |
| D32 | Annulation d'événement (F3) | Titre à recopier + motif obligatoire avant que le bouton ne soit actif. | Action irréversible à fort impact. |
